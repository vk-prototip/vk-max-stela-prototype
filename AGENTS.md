# Правила работы с веб-прототипом

## Обязательный контекст

Перед любыми изменениями полностью прочитать:

1. `../AGENTS.md` – постоянные правила проекта и приоритет источников.
2. `README.md` – команды и порядок входа.
3. `docs/PROJECT_STATE.md` – подтверждённое текущее состояние.
4. `docs/OPEN_QUESTIONS.md` – решения, которые нельзя принимать самостоятельно.
5. `docs/NAVIGATION.md` – границы каталогов.

Последнее прямое указание пользователя имеет высший приоритет. Если документы расходятся, зафиксировать расхождение и следовать приоритету источников из `../AGENTS.md`.

## Границы прототипа

- Не придумывать маршруты, миссии, функции продукта, реплики, результаты и переходы для заполнения пустого места.
- Не переносить внутренние комментарии и технические заметки в пользовательский интерфейс.
- Неподтверждённое помечать в документах как «рабочая гипотеза» или «требует согласования».
- Не редактировать файлы в `../01_Исходники`.
- Не копировать клиентские материалы в `public` или `src/assets` без явной необходимости и проверки прав на использование.
- Не хранить изменяемые сценарные решения в этом файле. Для них использовать `docs/PROJECT_STATE.md`, `docs/DECISIONS.md` и `docs/OPEN_QUESTIONS.md`.

## Архитектурные правила

- `src/app` отвечает за сборку приложения и глобальные провайдеры.
- `src/pages` содержит экраны верхнего уровня.
- `src/features` содержит самостоятельные пользовательские сценарии и их состояние.
- `src/components` содержит переиспользуемые проектные компоненты.
- Общие утилиты добавлять в `src/shared` только когда для них появится реальное содержимое.
- `src/content` содержит пользовательские тексты и сценарные данные с явным статусом происхождения.
- `src/types` содержит общие контракты данных.
- Не помещать сценарные тексты напрямую в компоненты, кроме временного технического экрана.
- Не создавать абстракцию до появления реального повторения или устойчивой границы ответственности.
- Сохранять строгую типизацию. Не использовать `any` без зафиксированной причины.

## Работа с текстами

Каждый сценарный текст должен иметь один из статусов: `client-verbatim`, `user-approved`, `working-draft`, `needs-approval`.

Для дословного текста указывать источник. Редакторскую сборку не выдавать за текст клиента. Соблюдать правила пунктуации и пользовательского текста из `../AGENTS.md`.

## Завершение каждой сессии

1. Выполнить `npm run typecheck`, `npm run test`, `npm run lint` и `npm run build`.
2. Визуально проверить изменённые экраны на целевых размерах, когда экраны уже появились.
3. Обновить `docs/PROJECT_STATE.md`.
4. Новые принятые решения добавить в `docs/DECISIONS.md`.
5. Новые неопределённости добавить в `docs/OPEN_QUESTIONS.md`.
6. Кратко обновить `docs/CHANGELOG.md` только при содержательном изменении базовой версии.
7. Не создавать отдельный журнал для каждого технического действия и не добавлять в документы большие выводы команд.
